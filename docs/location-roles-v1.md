# Фаза 2: доказовий контекст адрес, v1

Дата: 11.09.2026. Обсяг: перший консервативний крок Фази 2, без зміни UX.

## Поведінка

`src/addr.py` повертає всі розпізнані згадки адрес зі зміщеннями в тексті,
оригінальним написанням, фрагментом, роллю, причиною і версією правил.
Повтори з різними контекстами не губляться. Підтримано адреси з номером
та базовий формат вулиці без номера. Непідтримані формати ще потребують QA.

Сама відсутність слова «суд» більше не означає EVENT_LOCATION. Потрібні
явна дія і безпосередня прив'язка «по / на / біля / поблизу / за адресою».
Суд, проживання, робота, майно та установа мають пріоритет заборони.
Заперечення, процесуальний контекст, кілька адрес у фрагменті, різні місця
подій або конфлікт ролей одного місця не дають вибрати першу адресу.
Заголовок рішення не використовується як запасне місце події.

Це правила відбору, **не виміряна точність і не юридичне підтвердження події**.
Вони свідомо пропускають частину придатних описів. Реальний QA-набір,
precision, адміністративні межі, confidence геокодування та безпечний
просторовий fallback залишаються незавершеними пунктами ROADMAP.

## Зберігання і допуск

- Step1 атомарно записує сумісний рядок події та `address_evidence` в SQLite.
  Повторне витягування видаляє старий геокод цього документа.
- `location_evidence.confirmed_rows` повторно перевіряє версію, контекст,
  вибір адреси та збіг з поточним рядком. Його використовують геокодер і карта.
- Старі рядки й координати без контексту не проходять допуск. Нуль придатних
  записів зупиняє збірку до нового опублікування; попередній розгорнутий сайт
  автоматично не видаляється. Для нього потрібен окремий перевірений перезапуск.
- PostgreSQL sync переносить усі розпізнані ролі; старий CSV дає лише UNKNOWN.
  Повторні згадки агрегуються в evidence без втрати контексту. При повторному
  sync старі витягнуті зв'язки замінюються. Усі події лишаються `is_public=FALSE`.
- Контексти є внутрішніми даними: не додавати SQLite або evidence у публічний
  Git, артефакти Actions чи CSV. Поточний CSV-формат з 9 колонок не змінено.

## Перехід зі старих знімків

Збережіть резервну копію локальної `data/events.db`. Для поступового
повторного витягування використовуйте наявні офіційні `data/kyiv_*.csv`:

```powershell
$env:RECHECK_LOCATION_EVIDENCE = '1'
$env:MAX_DOCS = '1000'
python src/step1_download.py
python src/step1b_sync_postgres.py
python src/step2_geocode.py
```

`RECHECK_LOCATION_EVIDENCE` стосується CSV-черги (без DATABASE_URL).
Він повторно ставить у чергу старі записи без поточної версії evidence,
але не видаляє історію років, для яких немає локальних метаданих.
Успішний результат без адреси також вважається перевіреним, а помилка — ні.
Зберігайте цю локальну БД між запусками. Для PostgreSQL-черги перед повторним
витягуванням потрібно явно позначити обрані документи `needs_processing=TRUE`.
Sync із PostgreSQL виконують після витягування, задавши DATABASE_URL.

**Обмеження weekly Actions:** runner відновлює лише публічний CSV і не має
історичного evidence. Тому історичні адреси не підтягуються автоматично;
без нових підтверджених місць збірка зупиниться. До відновлення повного weekly
потрібне приватне довготривале сховище контексту та контрольний backfill.
Не обходити це обмеження прапорцем «довіряти старим адресам».

## Перевірка

```text
python -m unittest discover -s tests -v
```

Штучні регресійні тести перевіряють негативні ролі, неоднозначність,
простежуваність контексту, старі/зіпсовані докази й допуск геокодера.
Окремий job CI запускає інтеграційні тести в PostgreSQL/PostGIS:
повторний sync без дублів, зміна EVENT_LOCATION на COURT/UNKNOWN,
деактивація і rollback транзакції. Це не замінює ручний QA реальних рішень.
